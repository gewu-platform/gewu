## 一、排期原则

1. **先修回归，再补能力**：v2.1.0 沙箱把 MCP 工具默认阻断了，属于能力回归，必须最先修
2. **先补"改代码不心虚"的底座**：可观测与测试缺失时，任何新功能都是盲改

## V2.2.0 · 能力恢复 + 可观测底座（P0，立即）

### 背景：必须先修的回归

v2.1.0 引入沙箱后，`external` 风险级默认策略为 `sandbox`，而沙箱适配器仅覆盖 `calculator`。
MCP 桥接工具默认风险级为 `EXTERNAL` → **逐次调用返回"暂无沙箱适配器"错误**。
即：**R3 插件仓库装好的工具，现在一个都跑不了。**

这是能力回归，不是新需求。

### A1 MCP 工具沙箱适配器（T1 优先级最高）

| 任务 | 内容 | 验收标准 |
|---|---|---|
| A1.1 桥接适配器 | 为 MCP 桥接工具提供沙箱适配路径：沙箱子进程代持 MCP 连接（server endpoint + 密钥经 stdin 单次传入，不落盘不进日志） | 装好插件的工具在默认配置下可正常调用 |
| A1.2 连接生命周期 | 子进程短连接（每调用建连→执行→退出）或长驻 worker（按性能实测二选一），不泄漏连接 | 连续 N 次调用无连接泄漏、无句柄堆积 |
| A1.3 密钥边界 | MCP 认证信息只经 stdin 传递，日志与 DB 不出现明文 | 日志与 DB 检索无明文密钥 |
| A1.4 降级可配 | 若某 MCP server 不适合沙箱（如流式长连接），可显式降级为 `direct` 并记录强告警 | 配置后可用，且有 ERROR 级告警留痕 |

> 备选方案：若 A1 成本过高，退一步为「MCP 工具默认风险级改为 `DYNAMIC` 并走直执行 + 强告警」，但需确认接受安全边界降低。

> **A1 实施记录（2026-11-02）：已按备选方案落地，原 A1.1 子 JVM 隔离方案经技术评估后放弃。**
>
> 评估依据（代码核实）：
> - MCP 工具执行本质是 `client.executeTool(raw)` 纯 HTTP/SSE 调用，**本地不执行任何代码**
> - 威胁模型差异：calculator 风险是本地 JS eval 逃逸（JVM 隔离有效）；MCP 工具风险是
>   远端服务返回恶意数据 + 远端副作用（本地进程隔离**不改变**远端风险）
> - 成本对比：子 JVM 方案需物化整个 MCP 客户端栈（当前仅物化 sandbox 包 + nashorn/asm），
>   且每次调用增加 500ms+ JVM 启动与 MCP 握手开销，换来**零本地安全收益**
>
> 实际落地（真实有效的控制点）：
> - `external` 风险级默认由 `sandbox` 改为 `direct`（恢复 MCP/插件工具可用）
> - MCP 调用有界：原生 `HttpMcpTransport.timeout` + `DefaultMcpClient.toolExecutionTimeout`
>   （默认 30s，可配），结果长度上限（默认 10 万字符，可配并标注截断）
> - 全程审计留档：server/tool/耗时/输出长度/是否截断/失败根因
> - `dangerous` 级仍强制 `sandbox`、`on-unavailable` 仍默认 `reject`、
>   calculator 仍 `DYNAMIC`——**本地代码执行风险仍受沙箱约束**
>
> 结论：A1.2/A1.3/A1.4 的验收目标（工具可用、有边界、有审计、可降级）已达成；
> A1.1 的「子进程代持连接」被证明是无收益的复杂度，不再实施。

### A2 OpenTelemetry-lite（T1）

| 任务 | 内容 | 验收标准 |
|---|---|---|
| A2.1 依赖接入 | `spring-boot-starter-actuator` + `micrometer-registry-prometheus` | `/actuator/health`、`/actuator/metrics`、`/actuator/prometheus` 可用 |
| A2.2 traceId 贯穿 | traceId 注入 MDC 与日志格式；每请求一个 traceId | 同一请求的所有日志可 grep 串起来 |
| A2.3 关键 span | LLM 调用、工具执行、RAG 检索、沙箱 spawn 各打 span（耗时/结果/错误） | 慢请求可定位到具体环节 |
| A2.4 沙箱父子透传 | 子进程协议增加 traceId 字段，子进程日志带同一 traceId | 沙箱内日志与父进程日志可关联 |
| A2.5 OTLP 导出（可选） | 支持 `OTEL_EXPORTER_OTLP_ENDPOINT` 导出到 Jaeger/Tempo | 配置后可看调用链 |

**为什么优先**：AI 链路深且慢（会话组装→RAG→LLM 多轮→工具→沙箱），无 traceId 时排障只能翻散落日志；且沙箱刚引入跨进程，这是最需要可见性的时点。

### A3 限流（T1）

| 任务 | 内容 | 验收标准 |
|---|---|---|
| A3.1 令牌桶 | Bucket4j（或自实现）：按用户 + 按接口维度限流 | 超限返回 429 + `Retry-After` |
| A3.2 LLM 专项 | `/api/chat*`、`/api/agent/chat*` 更严阈值（可配） | 脚本刷接口被快速拦截 |
| A3.3 与配额协同 | 限流（速率）与既有配额（总量）分层：先速率后总量 | 两者不冲突，错误码可区分 |

**为什么优先**：LLM 边际成本是钱，现有配额是「按用户总量」而非「时间窗速率」，挡不住突发脚本刷。

| Channels（消息平台接入） | OpenClaw | ❌ 不做 | 产品定位差异（自部署平台 vs 驻留助理），维护负担大 |
## 四、优先级判定依据（诚实口径）

| 能力 | 审计现状 | 判定 | 理由 |
|---|---|---|---|
| OpenTelemetry | 完全没有（无 actuator/micrometer/traceId） | **P0** | AI 链路深、沙箱跨进程，无 traceId 排障靠猜 |
| 限流 | 完全没有 | **P0** | LLM 成本攻击面，配额挡不住速率刷 |
| 评测 | 测试文件 0 个，无评测集 | **P0** | 改 prompt/换模型无回归基线=盲改 |
| 版本治理 | tag 规范、规划文档齐全；缺 CHANGELOG/Flyway | **P0（补齐项）** | 成本低、可信度收益高 |
| 安全约束 | Security+JWT+校验+配额+掩码扎实；缺限流/审计 | **P0 限流 / P1 审计** | 基础好，补两个真空 |
| 沙箱深化 | 适配器仅 calculator，MCP 被阻断 | **P0（回归修复）+ P1（扩展）** | 先修回归，再扩适配 |
| 可插拔架构 | 5 个真实扩展点在跑；缺 SPI/条件装配 | **P2** | 实践中已可插拔，形式化收益待第三方接入 |
| 蓝绿发布 | 有 Dockerfile/CI（只构建不部署） | **P2** | 单人单机无 SLA，提前消费 |
| 容器级沙箱 | 无 | **P1 评估 / P2 实施** | 进程级已够，除非跑不可信第三方代码 |
