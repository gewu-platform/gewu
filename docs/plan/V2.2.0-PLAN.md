# 格物 Gewu · v2.2.0 版本规划

> 状态：✅ 已完成（tag `v2.2.0`，后端 peels `e692472` / 前端 `e10834b`）
> 基线：v2.1.0（tag 后端 `6da490d` / 前端 `e10834b`）
> 日期：2026-11-02 开工、2026-11-02 收官
> 来源：`docs/plan/ROADMAP.md` V2.2.0 批次（六维度能力审计产出）

## 一、一句话定位

v2.2.0 = **能力恢复 + 可观测底座**：先修 v2.1.0 沙箱造成的能力回归，
再补上「改代码不心虚」的可观测与限流底座。

## 二、背景：必须先修的回归（不是新需求）

v2.1.0 引入沙箱后，`external` 风险级默认策略为 `sandbox`，而沙箱适配器仅覆盖
`calculator`；MCP 桥接工具默认风险级为 `EXTERNAL` → **逐次调用返回「暂无沙箱适配器」**。
即 R3 插件仓库装好的工具，在 v2.1.0 默认配置下一个都跑不了。

## 三、需求 → 批次映射

### A1 MCP 工具恢复可用（P0，最高优先）

| 任务 | 内容 | 验收标准 |
|---|---|---|
| A1.1 方案评估 | 判定 MCP 工具是否需要 JVM 隔离 | 产出技术与威胁模型对照结论 |

## 四、实施记录（实际交付）

| 批次 | commit | 内容 |
|---|---|---|
| A1 | `3d6b4d6` | MCP 工具改有界直执行：`external` 默认 `direct`、原生 `HttpMcpTransport.timeout` + `DefaultMcpClient.toolExecutionTimeout`（30s 可配）、结果 10 万字符上限、审计留档 |
| A2 | `386ad17` | actuator + micrometer-prometheus；`TraceIdFilter`（MDC + 日志 `%X{traceId}` + finally 清理 + 响应头回写 + 输入清洗）；沙箱三段协议 traceId 透传 |
| A3 | `e692472` | 进程内令牌桶 `RateLimitService` + `RateLimitFilter`（仅拦 `/api/chat`、`/api/agent/chat`，429 + Retry-After） |

**A1 方案变更（重要）**：原计划把 MCP 客户端搬进子 JVM，经代码核实后放弃——
MCP 执行本质是 `client.executeTool()` 纯 HTTP/SSE 直通，**本地不执行任何代码**，
JVM 隔离对远端风险零收益，却带来每次 500ms+ 开销。改为「有界直执行」，
风险控制落在真正有效的层面（超时 / 结果上限 / 审计）。

**同批修复的三个真问题**：
1. 沙箱物化缓存未随 jar 失效（重打包后仍用旧 worker class）
2. `logging.pattern` 误插导致启动失败（Failed to bind `logging.level`）
3. Redis 不可达把整体 health 拉成 DOWN（Redis 本为可选加速层，改为不参与整体判定）

## 五、验收结果

- `actuator/health` 200 UP（db / diskSpace / ping）
- `actuator/prometheus` 179 条指标（`jvm_memory`、`http_server_requests`、`process_uptime`、`jvm_gc` 均在）
- 自定义 `X-Trace-Id` 在响应头回显，并贯穿认证与沙箱子进程日志
- 限流：非对话接口 30 次零 429；对话接口第 11 次起 429（容量 10），`Retry-After=2`，等 4 秒恢复
- 编译打包 EXIT=0

## 六、Non-Goals（本版明确不做）

容器级沙箱、K8s/Helm、多租户计费、Starter SDK、子 Agent 再派发、
API `/v1` 前缀、蓝绿发布编排。

## 七、决策记录

- 2026-11-02：MCP 工具不做 JVM 隔离，改有界直执行（依据：本地零代码执行 + 成本对照）
- 2026-11-02：限流用进程内令牌桶而非 Redis（Redis 为可选层，强依赖会在故障时失去保护；多实例精确限流记入 V2.5.0）
- 2026-11-02：Redis 不参与整体 health 判定（可选加速层，不可达应降级而非拉低服务健康）
