## 三、深度分析与取舍

### 3.1 会话上下文管理（差距最大，P0）

现状仅有 micro-compaction（截断单条超长工具结果），无会话级压缩。工具循环每轮携带完整历史 + 全量 skill 注入，长会话与工具密集场景下 token 累积不可控，触顶后请求直接失败，用户无感知无自救手段。对标双方均以「阈值触发摘要压缩 + 交接文档续跑」解决。取舍：压缩摘要由当前会话模型生成（不引入额外模型依赖）；压缩点与会话留档对齐（摘要落库可审计）。

### 3.2 插件连接生命周期（P0）

安装时尽力连接、失败保持登记态是 V2.6.0 的刻意简化（避免占位端点阻塞安装）；但缺状态跟踪意味着「端点中途恢复」这一常见场景（本地 MCP server 重启、网络恢复）无法自愈，必须卸载重装。对标双方均维护连接状态机。取舍：状态轮询探活（周期 + 手动刷新）而非事件订阅——实现简单且覆盖核心场景；桥接工具清单随状态变更增量刷新。

### 3.3 子代理并行派发（P1）

`agent_dispatch` 同步单发，master 派发 N 个子任务耗时 = 各子任务之和。Claude Code 单轮多 Task 并行、OpenClaw 后台 spawn + 收集器。格物的工具循环基于 langchain4j，工具执行在请求线程内，并行化需引入异步执行 + 结果聚合 + 事件流标记（哪个 worker 的 delta）。取舍：并行实现收敛在 dispatch 工具层（批量派发工具 + 等待全部完成 + 结构化聚合回传），不改工具循环骨架；单发工具保留（简单任务零开销）。

### 3.4 编排层级（决策：维持一层）

多层递归派发（子 Agent 再派发）在 OpenClaw 支持（后代树），Claude Code 有限支持。格物 V1.1.0 显式设计为「编排树仅一层」（子执行内 agent_dispatch 双层拒绝）。评估：多层带来循环风险、成本失控、结果聚合复杂度陡增，当前业务场景一层树已覆盖；**维持现状并保留双保险拒绝逻辑**，出现真实多层需求时重评（决策记录）。

### 3.5 Skill 渐进披露（P1，承接 R1）

已立项（见 R1）。补充决策：不引入「按对话内容动态挑选技能」的路由层——R1 的按需取用已把选择权交给模型（与对标方一致），路由层属于过度设计。

## 五、非目标与决策记录

| 决策 | 理由 |
|---|---|
| 多层递归编排不做 | **对标强化（2026-11-17）**：Claude Code 的 Task 子代理同为显式一层设计（subagent 内不能再 spawn），格物与 CC 对齐而非落后；OpenClaw 支持多层但依赖其成套治理设施（会话树/预算/取消传播），单独搬「多层」而无治理设施才是真风险。维持一层，决策升级为与 CC 对齐的确定性结论 |
| 动态技能路由层不做 | **对标强化（2026-11-17）**：OpenClaw 与 Claude Code 均无路由层（渐进披露是终态，模型自主按需取用）。R1 已使格物与对标方机制对齐，决策从「条件性重评」升级为永久决策。唯一例外：成本敏感场景需强制限定注入技能集——那是 Agent 配置问题（勾选已支持），不需要路由层 |
| Hooks/automations 系统延后 | **定性修正（2026-11-17）**：对标双方均重度依赖（CC hooks 是生态核心、OpenClaw automations 是平台支柱）——准确说不是「无对标」而是「能力性质不匹配」：hooks 属开发者向能力，格物当前用户群为终端用户向；且审批网关本质已是 PreToolUse 钩子的特化（骨架已存在）。触发条件具体化：① 用户需要自定义工具拦截/自动化规则；② Agent 需要定时/事件驱动触发（cron 类任务）。**2.8.1 复核结论：不纳入**（无用户需求触发且属大特性，建议 V2.9.0 评估） |
| MCP resources/prompts 完整桥接延后 | resources 已以工具形态桥接，prompts 无使用场景。**新观察项（2026-11-17 对标识别）**：streamable HTTP 传输为 MCP 规范演进方向（Claude Code 已支持三传输），比 stdio 更契合格物容器部署形态。**2.8.1 复核结论：不纳入**（当前仅 http_sse 样例且无真实 MCP server 需求驱动），需求触发后实施 |
