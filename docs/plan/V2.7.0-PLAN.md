> 状态：**规划中**（2026-11-12 立项）
> 基线：v2.6.0（tag 后端 `b465811` 前置 / 前端 `96f4f93` 前置）
> 日期：2026-11-12 立项
> 来源：① FastGPT 官方设计源码（`labring/FastGPT` `packages/web/styles/theme.ts`）对标评估；

## 一、一句话定位

v2.7.0 = **UI 设计系统化**（从「有 token 表」到「有设计体系」）+ **部署形态复盘**（容器化的代价与合理性再评估）。

## 二、方案取舍

| 方案 | 评估 | 结论 |
|---|---|---|
| 逐页手工调样式 | 前端页面 8 个，逐个调色值/阴影，改动分散且下次加页面又漂移 | 不采用 |
| 引入完整组件库替换（如照搬 FastGPT 的 Chakra 体系） | 现有基于 Ant Design Vue 的 8 个视图全量重写，成本极高且丢失 gewu 自身性格 | 不采用 |
| **扩展现有 CSS 变量为完整设计体系**（色阶/阴影/圆角/字号刻度），逐视图替换合规 | 增量可控，保留 AntD 与既有结构，一次投入长期受益 | **采用** |

范围说明：**学 FastGPT 的系统性纪律，不克隆其界面形态**。gewu 保留藏青导航（`--nav: #1E3A5F`）与几何「格」品牌标识，避免成为「另一个 FastGPT」。

## 四、待解决问题清单（来自本轮开发复盘）

### 4.1 容器化边界类（最高优先级）

| # | 现象 | 根因 | 性质 |
|---|---|---|---|
| P1 | `gewu-init.sql` 建库语句缺失 / 库名不统一 | 脚本同时充当 `docker-entrypoint-initdb.d`，建库由 `POSTGRES_DB` 承担；改库名对已初始化数据卷不生效 | 契约不清 |
| P2 | 数据卷已存在时改 `GEWU_DB_NAME` 无效，服务 FATAL 连不上 | Docker 卷仅首次初始化执行建库与 init 脚本 | 认知盲区 |
| P3 | Skill 目录「填写真实目录仍提示不存在/不可读」 | 默认值为宿主机 Windows 路径，容器内不存在 | 硬编码宿主机路径 |
| P4 | 插件安装报「无法连接端点」 | 内置样例端点为 `localhost:800x`（容器内 localhost 是容器自身） | 占位数据误导 |
| P5 | 宿主机 MCP server 容器内不可达 | server 绑定 `127.0.0.1`；须 `0.0.0.0` + `host.docker.internal`，且宿主机进程会被系统回收 | 网络边界 |
| P6 | 构建镜像报 `docker-credential-desktop not found` | Docker Desktop 装在用户目录、bin 不在 PATH | 环境准备 |

> **复盘结论（待 B3.2 决策确认）**：以上 6 项的共性不是「容器化本身有问题」，而是**容器的隔离边界没有在项目契约里显式声明**——资源（数据库/文件目录/网络端点）在宿主机与容器两侧各有一份语义，"哪一侧生效"从未写进文档，导致每次都在运行时才暴露。因此**倾向维持容器化**（交付价值明确：环境一致性、一键部署），但必须补齐「边界契约 + 部署检查清单」，并把开发期与交付期的运行形态区分开。

1. `npm run build` + `mvn -o test` 全绿
