# ADR-0002 · 部署形态评估：容器化是否仍然合理

> 状态：**草案待确认**（2026-11-12 立项评估）
> 关联：ROADMAP V2.7.0 批次 3（B3.1~B3.3）
> 触发来源：2026-11-10 ~ 11-12 联调期内因「宿主机 ↔ 容器」边界引发的连续故障

## 一、问题陈述

近三天的开发与联调中,故障高度集中在容器边界而非业务逻辑:

| # | 现象 | 根因 | 影响面 |
|---|---|---|---|
| 1 | 新代码部署后服务 FATAL: `database "gewu" does not exist` | 数据卷为旧版本初始化,改 `GEWU_DB_NAME` 对已存在卷不生效 | 服务不可用 |
| 2 | 公共 Skill 目录「填写真实目录仍提示不存在/不可读」 | 默认值为宿主机 Windows 路径,容器内不存在 | 功能不可用 |
| 3 | 插件安装报「无法连接端点」 | 内置样例端点为 `localhost:800x`,容器内 localhost 指向容器自身 | 功能不可用 |
| 4 | 宿主机 MCP server 容器内不可达 | server 绑定 `127.0.0.1`;需 `0.0.0.0` + `host.docker.internal` | 功能不可用 |
| 5 | 镜像构建失败 `docker-credential-desktop not found` | Docker Desktop 安装于用户目录,其 bin 未入 PATH | 构建阻塞 |
| 6 | Docker Desktop 两小时内崩溃 3 次 | 宿主机内存紧张(15.7G 总量余 3.7G) | 全环境中断 |

## 二、根因归类（关键判断）

6 项故障按性质可分为两类,不应混为一谈:

**A 类 · 契约缺失(占 4 项)**:第 1~4 项的共同点不是「容器化有缺陷」,而是**容器的隔离边界从未写入项目契约**。数据库、文件目录、网络端点这三类资源,在宿主机与容器两侧各有一份语义,「哪一侧生效」只在运行时暴露,文档中无任何声明。若在宿主机直跑,这些问题会以「端口冲突/路径不存在」等另一种形态出现,并不会消失。

**B 类 · 环境准备(占 2 项)**:第 5 项是 Docker Desktop 的安装位置问题(一次性配置);第 6 项是宿主机内存不足(硬件约束,与容器化无关——但容器化放大了后果,因为内存压力直接杀死 WSL2 后端)。

## 三、方案评估

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **① 维持容器化 + 补齐边界契约** | 保留环境一致性、一键交付、与既定交付形态(R3/T2 容器化)一致;A 类问题通过文档与检查清单可根治 | 仍需开发者理解边界;对宿主机内存有硬要求 | **推荐** |
| ② 开发期宿主机直跑、交付期容器化 | 开发期无边界问题,反馈最快 | 双形态漂移:「本地能跑」不代表「镜像能跑」,验收需双跑;依赖本机 PG/Redis/MinIO 齐全 | 部分采用(开发期默认直跑,提交前容器验一次) |
| ③ 完全去容器化 | 彻底消除边界问题 | 放弃一键部署与环境一致性,与产品定位(交付给他人部署)冲突 | 不采用 |

## 四、结论与行动

**结论:维持容器化,但契约必须显式化。** 容器化本身不是问题来源,「边界未声明」才是。

落地行动(纳入 V2.7.0 批次 3):

1. **资源边界契约**:在 `docs/DEPLOY.md` 明确三类资源的「生效侧」——
   - 数据库:卷初始化语义(仅首次生效)、改名/迁移操作步骤
   - 文件目录:宿主机路径 → 容器挂载点映射表,禁止硬编码宿主机路径作为默认值
   - 网络端点:容器内访问宿主机的写法(`host.docker.internal`)、容器间互访(服务名)、宿主机服务必须绑 `0.0.0.0`
2. **部署边界检查清单**:新部署前逐项勾选(卷状态/挂载/端口/端点/内存),不通过不开工
3. **开发期形态**:默认宿主机直跑(快),涉及挂载/网络/镜像的改动必须容器验证一次
4. **硬性要求**:`docs/DEPLOY.md` 写明最低内存(建议 ≥8G 可用)与 Docker Desktop 资源上限设置方法
5. **内置样例治理**:占位端点必须在 UI 上明示「占位,不可直连」,或替换为可运行样例

## 五、重启议题的触发条件

出现以下任一情况时重新评估本决策:

- 容器化带来的运维成本连续两个版本高于其交付收益
- 目标部署环境无法提供容器运行时(客户侧限制)
- 出现容器化无法满足的交付要求(如必须裸机安装包)
